# Техническое задание (ТЗ):

**Переход проекта CloudPosBridge на “чистую архитектуру” с инфраструктурными расширениями (очередь, мониторинг, fault-tolerance)**

---

## **1. Общая цель**

Разработать и внедрить новую архитектуру, в которой:

* Бизнес-логика и сценарии отделены от инфраструктуры и реализации,
* Все внешние системы (ККТ, банк, Честный Знак и др.) инкапсулированы за интерфейсами,
* Поддерживаются инфраструктурные паттерны: очередь для отложенных операций, мониторинг состояния интеграций, гибкая конфигурируемость,
* Все компоненты покрываются юнит-тестами и легко подменяются.

---

## **2. Архитектурные требования**

**2.1. Разделить код на слои:**

* **Domain (домен):** бизнес-объекты и бизнес-правила (например, Check, Payment, BankTransaction).
* **Application (use-cases):** сценарии работы (“продажа”, “возврат”, “передача чека в ЧЗ”, “печать банковского слипа”, и т.д.).
* **Interfaces (ports):** интерфейсы для внешних зависимостей (например, PrinterInterface, BankTerminalInterface, HonestSignGateway).
* **Infrastructure (adapters):** реализации интерфейсов (например, GoBankTerminalAdapter, HttpHonestSignGateway, HonestSignQueue, FileSettingsStorage, мониторинг и др.).
* **API/Web layer:** REST API, контроллеры, web-интерфейс (минимальная логика).

**2.2. Все зависимости направлены внутрь**
(внешние адаптеры зависят от интерфейсов ядра, а не наоборот).

---

## **3. Функциональные чекпоинты (этапы)**

### **Чекпоинт 1. Базовое проектирование**

* [ ] Провести аудит существующего кода, выделить бизнес-логику, инфраструктурные зависимости, интеграции.
* [ ] Составить схему текущих потоков данных и точек интеграции (ККТ, банк, Честный Знак, очередь и т.д.).
* [ ] Утвердить границы слоёв и перечень интерфейсов для внешних интеграций.

---

### **Чекпоинт 2. Введение доменных моделей и интерфейсов**

* [ ] Создать структуры/классы для доменных моделей (Check, Payment, BankTransaction, MarkingCode и др.).
* [ ] Определить интерфейсы (PHP-интерфейсы, абстрактные классы) для:

  * Принтеров чеков (`PrinterInterface`)
  * Банковского терминала (`BankTerminalInterface`)
  * Взаимодействия с Честным Знаком (`HonestSignGateway`)
  * Хранилища настроек (`SettingsStorageInterface`)
* [ ] Описать возможные ошибки и их обработку через исключения или result-классы.

---

### **Чекпоинт 3. Выделение сценариев (use-cases) в отдельный слой**

* [ ] Создать отдельные классы сценариев для основных операций:

  * `PrintCheckUseCase`
  * `ProcessBankOperationUseCase` (Pay, Return, CloseShift)
  * `SendToHonestSignUseCase`
  * и др. по проекту.
* [ ] В use-case должны использоваться только интерфейсы, не реализации.

---

### **Чекпоинт 4. Реализация инфраструктурных адаптеров**

* [ ] Перенести весь код работы с внешними системами в отдельные адаптеры:

  * Адаптер к Go-бинарю/COM для банка
  * Адаптер к HTTP-API Честного Знака
  * Адаптер к файловой очереди/базе для отложенных отправок (HonestSignQueue)
  * Адаптер к системам мониторинга/health-check
  * Адаптер для чтения/записи конфигов
* [ ] Каждый адаптер реализует соответствующий интерфейс.

---

### **Чекпоинт 5. Очередь и отложенные операции**

* [ ] Реализовать очередь для отложенной отправки чеков/маркировок в Честный Знак (может быть файловая или в базе).
* [ ] В use-case/адаптере предусмотреть логику:

  * Если API ЧЗ недоступен — отправлять в очередь.
  * При восстановлении связи — автоматическая отправка из очереди.
* [ ] Продумать мониторинг состояния очереди.

---

### **Чекпоинт 6. Мониторинг и health-check**

* [ ] Реализовать отдельный сервис/модуль мониторинга состояния интеграций:

  * Проверка доступности API ЧЗ, банка, ККТ, локального модуля.
  * Общий статус системы для вывода на dashboard и REST API `/api/health`.
* [ ] Прописать сценарии оповещения (логирование, email, или просто файл/метрика).

---

### **Чекпоинт 7. Конфигурирование и динамические режимы**

* [ ] Вынести настройки всех интеграций и режимов работы в конфиг (json, yaml, env).
* [ ] Позволить гибко управлять таймаутами, режимами (разрешительный/строгий), retry-логикой, кешами через конфиг.

---

### **Чекпоинт 8. Тестирование**

* [ ] Покрыть все use-cases юнит-тестами (mock-интерфейсы, заглушки).
* [ ] Проверить корректность работы очереди, health-check, fallback-логики (работа при недоступности API).
* [ ] Провести интеграционное тестирование всех сценариев через API.

---

### **Чекпоинт 9. Документация**

* [ ] Обновить/дописать документацию по архитектуре, интерфейсам, примерам интеграции новых адаптеров.
* [ ] Составить схему зависимостей, описание бизнес-сценариев, способы расширения.

---

## **4. Результаты и приёмка**

* Код соответствует архитектуре (чёткое разделение слоёв, покрытие интерфейсами).
* Любой новый адаптер реализуется без изменения use-case.
* Очередь и мониторинг функционируют корректно (можно выключить ЧЗ или банк — данные не теряются).
* Добавление новой интеграции (например, другого банка) делается “без боли” — только новым адаптером.
* Вся логика тестируема, покрыта юнит-тестами.

---

## **5. Сроки и организация работы**

* Каждый чекпоинт — самостоятельный этап, приёмка — по завершению каждого этапа (pull request + короткое ревью и тест).
* Структура репозитория согласуется после чекпоинта 1.
